# Contributing

Этот репозиторий — исследовательский код для статьи (планы E0–E13 в
`docs/experiments.md`). Основной риск здесь не стиль кода, а тихая порча
численных результатов: изменение конфига по умолчанию, дрейф между вариациями
сравнения, чекпоинт, переставший грузиться. Правила ниже написаны в первую
очередь против этого.

## Быстрый старт

```bash
uv sync --dev        # или: make install
make hooks           # pre-commit: ruff check/format при каждом коммите
make check           # lint + format-check + pytest — то же гоняет CI
```

Полный список режимов запуска (smoke, DDP, resume, значимость и т.д.) —
[docs/running.md](docs/running.md).

## Прежде чем менять код

1. **Прочитайте [docs/architecture.md](docs/architecture.md)** — что разделяют
   между собой варианты сравнения (общие блоки в `models/blocks.py`) и что нет.
2. **Правило К2 (общий рецепт)**: `training.*` в `configs/base.yaml` —
   один на все варианты. Если нужно поменять LR/batch/loss для одного варианта
   — это уже другой эксперимент, а не правка инфраструктуры; не трогайте
   `base.yaml` ради одного варианта, переопределяйте явным `--set` в команде
   запуска этого эксперимента.
3. **Численный паритет с легаси-ноутбуками обязателен для `models/`.**
   Любое изменение в `models/` должно:
   - сохранять ключи `state_dict` (легаси-чекпоинты продолжают грузиться) —
     см. `tests/test_models.py::test_trm_state_dict_keys_stable`;
   - не менять forward numerically для существующих конфигов флагов.
   Проверяется двумя способами:
   ```bash
   # 1. Если есть легаси-чекпоинт под рукой:
   TRM_LEGACY_CHECKPOINT=/path/to/best_mrr.pt make parity

   # 2. Если чекпоинта нет (например, чистый рефакторинг): сравнить старую и
   #    новую модель побитово на одном сиде через временный git worktree —
   #    см. подход в git log (коммит рефакторинга моделей 0.3.0) как пример.
   ```
   Рефакторинг (переименования, вынос общей базы, dedup) — можно и нужно;
   любое отклонение чисел — нет, если оно не заявлено как явное изменение
   поведения (в PR и CHANGELOG).

## Тесты

- `make test` — обязателен перед любым PR. Он включает синтетический e2e-тест
  Trainer'а (`tests/test_trainer.py`): обучение → чекпоинты → resume → финальный
  dev-eval на CPU за секунды. Если вы трогаете `training/trainer.py`,
  `training/optim.py` или `data/datasets.py` — убедитесь, что эти тесты
  ловят ваш кейс; если нет, добавьте сценарий, а не полагайтесь на ручную
  проверку.
- Новая архитектура/лосс/датасет — добавляйте тест в соответствующий
  `tests/test_*.py`, не создавайте отдельный ad-hoc скрипт в `scripts/`.
- Не понижайте покрытие проверок конфига (`tests/test_config.py`): опечатки в
  именах секций/ключей должны падать с ошибкой, а не проглатываться.

## Стиль кода

- `make fmt` перед коммитом (или `make hooks` — тогда автоматически).
  `make check` = `ruff check` + `ruff format --check` + `pytest`; CI гоняет то
  же самое (`.github/workflows/ci.yml`).
- Без комментариев, объясняющих *что* делает код (имена уже это делают).
  Комментарий — только когда что-то не очевидно из кода: скрытый инвариант,
  обходной путь вокруг конкретного бага, численное соответствие легаси.
- Не добавляйте абстракции/конфигурируемость под гипотетическое будущее.
  Если план (`docs/experiments.md`) явно требует параметра — добавляйте;
  если это "а вдруг пригодится" — нет.
- Не добавляйте новые тяжёлые зависимости без необходимости: самописные
  метрики/конфиг-лоадер — осознанное решение (паритет с ноутбуками, без
  Hydra/ir-measures в базовом окружении); их не стоит заменять попутно.

## Конфиги

- Локальные пути — только в `configs/local.yaml` (в `.gitignore`); шаблон —
  `configs/local.example.yaml`. Никогда не коммитьте реальные пути машины в
  `base.yaml`/`configs/variants/*.yaml`.
- Новый гиперпараметр — добавляйте в соответствующий dataclass в
  `src/trm_reranker/config.py` с дефолтом, не как "магическое" значение внутри
  кода; проверяйте `--print-config`, что он реально долетает.
- Новый вариант сравнения (`configs/variants/<name>.yaml`) должен явно
  документировать, чем он отличается от K1/K2 (см. существующие файлы —
  комментарий в шапке).

## Данные и артефакты

- Не коммитьте датасеты, чекпоинты, `runs/`, манифесты с реальными путями —
  всё это либо в `.gitignore`, либо не должно попадать в репозиторий вовсе.
- Формат манифестов (`prep_manifest.json` / `run_data_manifest.json`) и
  hard-negatives JSONL — стабильные контракты между шагами пайплайна;
  меняя схему, повышайте `schema_version` и обновляйте валидацию в
  `data/manifests.py`, а не тихо переименовывайте ключ.

## Коммиты и PR

- Коммит — одна логическая правка; сообщение объясняет *зачем*, а не
  пересказывает диф (см. `git log` для стиля).
- В описании PR — что именно проверено (`make check`, parity-прогон при
  изменении моделей, живой прогон CLI при изменении скриптов).
- Обновляйте `CHANGELOG.md` (Keep a Changelog) для любого изменения,
  видимого пользователю CLI/конфига — не только для релизов.
- Fork/upstream: `origin` — личный форк, `upstream` — основной репозиторий.
  PR обычно идут в `upstream`; синхронизируйте `main` перед началом работы
  (`git fetch upstream && git merge upstream/main`).

## Если сомневаетесь

Задача — воспроизводимая статья, а не production-сервис. При конфликте между
"чище архитектурно" и "не рискует численными результатами" — выбирайте
второе, либо явно проговаривайте риск в PR и гоняйте parity-тест.
